## 首页 dashboard 压住 TP 调试面板（trace）

**反馈**：滚动层级修好后，「层级比 tp 调试模式的右下角固定悬浮 think_page_trace 更高，会覆盖 trace」。

**诊断**：
- `.dashboard-shell{overflow:hidden}` 会形成**层叠上下文**（即使自身 `position:static`），其内元素进入该上下文后，与根上下文里的元素不再平分层级。
- 框架页那份 trace 在 `.wrapper` 内、iframe 之外，`z-index:999999` 在根上下文中计算 → 被 `.dashboard-shell` 盖住。
- 项目现状：`app/` 与 `public/assets/` 里**完全没有** trace 相关样式，vendor 的 `999999` 是原样直出。

**层级基线**（判断层级冲突时先查这三个值）：
| 用途 | z-index | 出处 |
|---|---|---|
| layer 弹层基准 | `19891014` | `libs/fastadmin-layer/dist/layer.js` 的 `config.zIndex`，多弹层依次 +1，shade 是 `s-1` |
| 水印 | `100000` | `view/index/index.html` |
| TP trace | `999999` | `vendor/topthink/think-trace/src/tpl/page_trace.tpl` |

**改动**（`app/admin/view/dashboard/index.html` 内联样式，1 处）：加 `#think_page_trace{z-index:1000001}` —— 让框架页 trace 重新压过 `.dashboard-shell`，同时仍低于弹层。

**未做（有意）**：iframe **内页**那份 trace 恒 `999999`，而 `.main-header`(1030)、`.lc-panel`(1050) 在**父文档**里 —— 父文档定位元素一律绘制在普通 iframe 之上，内页 trace 再高的 z-index 也出不来。用户选择「只修首页」，未动框架层。该问题只影响本机开发（`APP_DEBUG=true`，上线 false 后 trace 不注入）。

### 更正：首版修法无效，必须加 `!important`

首版写成 `#think_page_trace{z-index:1000001}`（无 `!important`），**用户实测仍不可见**。原因：
- 本项目 vendor 的 `page_trace.tpl` 把样式写成**元素内联 style**（`style="...z-index: 999999..."`），**内联样式优先级高于任何非 `!important` 的外部规则** → 普通 id 选择器 `(1,0,0)` 压不住内联。
- 修正为 `z-index:1000001 !important`。注意：内联 `999999` 若也是 `!important` 则内联仍胜；本项目内联**无** `!important`，所以外部 `!important` 可覆盖，实测成立。

**重要事实：两个项目的 trace 模板写法不同，修法不能照搬。**
| | rocket-admin | tp8-fastadmin |
|---|---|---|
| `.tpl` 写法 | 元素**内联 style** | `<style>` **CSS 块** |
| `999999` 出现处 | 1 处（`#think_page_trace`） | 3 处（`trace`/`trace_close`/`trace_open`） |
| 覆盖写法 | **必须** `!important` | 普通规则即可（仍统一加 `!important` 防日后模板升级） |

另注：`#think_page_trace_open`（右下角可见的黑色耗时条）本项目内联样式里**没有 z-index**（仅 `position:fixed`，即 `auto`），它在 `#think_page_trace` **内部** → 抬高外层容器即可带上来，无需单独处理。

## 组织架构插件 vs tp8-fastadmin tenant 独立子平台（选型调研，未落地）

**需求**：为 rocket-admin 补充「不同人看同一列表看到不同数据」的能力，两个候选：官方 `department` 插件（1.1.6 regular，商业授权）vs 上游 `tp8-fastadmin/app/tenant` 多租户子平台。

**插件 `department` 实测要点**（解压 `E:\phpstudy_pro\extraproject\插件包\department-1.1.6-regular.zip`）：
- 只有 2 张表：`{prefix}department`、`{prefix}department_admin`；`install.sql` 无 `shop_id`/租户概念（**不是多租户**）。
- 安装/升级会 `ALTER TABLE {prefix}admin ADD data_scope tinyint`（`Department.php:90-98`）→ 破坏性 DDL，卸载不回收。
- 数据隔离面极窄：只覆盖 `department/admin` 一个控制器 + 手写 `Admin::checkDataAuth()`／`getChildrenAdminIds()`（字符串拼 SQL）。**对全站业务表零作用** —— 不注入 `Backend::buildparams()`/dataLimit。

- 源码为 TP5.1 命名空间（`think\Addons`/`think\Db`/`think\Lang`/`think\Loader`）→ 移植 TP6 需改造。

**上游 tenant 子平台结构**（重要，避免误判）：
- `app/tenant` 是**完整独立的第二个后台应用**（自己的 Session 命名空间 `tenant`、自己的 `auth_group`/`auth_rule`/`admin`/`log`/`config`/`attachment`/`command` 表），不是管理端的一个模块。平台侧入口 `app/admin/controller/tenant/{Shop,Package,Grant,Rule,Category}.php`。

- 菜单级授权：`TenantPermissionService::getAvailableRuleIds()` = 套餐规则 ∩ 单租户增值授权 ∩ 全部规则；`AdminAuth::getRuleIds()` 对超管也做套餐收敛（`'*'` → 套餐可用集），`isSuperAdmin()` 有意用 `parent::getRuleIds()` 不受套餐影响。
- **仓库里没有真正的租户业务控制器**（`app/tenant/controller` 只有 auth/general/user 等基础功能 + `tenant_category`），业务在 `im_sys_*` 表（当前 DB 里不存在）→ 是一套**待二开的租户基座**。参考证据：`im_tenant_command` 记录了 `php think crud --controller=shop/Good|Order|GoodCategory|GoodStorage` 的建表命令。
