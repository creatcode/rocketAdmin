## 次栏选项卡选中态 —— 方案调整：改为方案 C（用户看过后改选）

上一节是第一版（容器白底 + 选中项浅蓝底 `#f0f5ff`）。用户看完改选**方案 C 变体 1**：容器浅底 + 选中项白卡片 + 主色文字。

**最终实现**（`skin-white.css`，紧随 `#secondnav .nav-tabs>li::before` 排除规则之后）：
```css
.skin-white #secondnav { background: #f6f8fb; }
.skin-white #secondnav .nav-tabs>li { box-sizing: border-box; background: transparent; }
.skin-white #secondnav .nav-tabs>li.active {
    background: #fff;
    border: 1px solid #dcdfe6 !important;
    border-radius: 4px !important;

.skin-white #secondnav .nav-tabs>li.active>a { color: #165dff !important; }
```

**四个必须注意的实现点**：
1. 未激活 `li` 必须显式 `background: transparent` —— 否则 baseline `backend.css:756` 的 `background:#fff` 会在 `#f6f8fb` 容器上留下一个个白块。
2. `border`/`border-radius` 必须带 `!important` —— 皮肤自身的 `.skin-white #secondnav .nav-tabs>li`（`skin-white.css:287`/`:289`）已是 `border:none !important`/`border-radius:0 !important`，特异性虽低但 `!important` 必须对等才压得住。
3. `>a` 的主色文字必须带 `!important` —— baseline `backend.css:760` 是 `color:#495060 !important`。
4. **`box-sizing: border-box` 是必需的，不是可选**：bootstrap.css **没有**全局 `*{box-sizing:border-box}`（只有 hr/input[type=checkbox]/input[type=search] 三处），li 默认 content-box，加 1px 边框会让总高从 30px 变 32px，比邻居高 2px。border-box 下 `height:30px` 含边框，与未激活项对齐；同时 a 的内容区正好剩 28px，与其 `line-height:28px` 吻合。

**几何核验**：`li` 高度 30px（`backend.css:753`）、`a` 行高 28px（`:763`）、容器 44px / `padding:5px 10px`（`:730`/`:737`）。白卡片圆角 4px、边框 `#dcdfe6`，文字 `#165dff` 与首栏一级菜单选中态一致（两行视觉语言统一）。

已重建 `backend.min.css`，4 条规则均在产物中，括号配平 246/246。方案 C 的容器浅底同时解决了「首栏/次栏两行同为白底糊在一起」的层级问题。

### 核心方法：官方给意图，写法按本项目内核改写

参照物是**兄弟项目 `tp8-fastadmin`（TP8 / think-orm 4.0.51 / PHP>=8.0）**，它已经把这些修复都做过了 → 提取其实现，再逐项核对本项目内核（**TP6 / think-orm 2.0.62 / PHP>=7.4.3**）能否照搬。

**三处必须改写的内核差异（照抄必崩）**：
| 官方/兄弟项目写法 | 本项目实际 | 本项目正确写法 |
|---|---|---|
| `\think\facade\Db::quote($v)` | think-orm **2.0.62 与 4.0.51 都没有 `quote` 方法** → `DbException: method not exist:think\db\Query->quote` | 保留 `'\'' . addslashes((string)$v) . '\''` |

## 进度条加百分比（16:10 追加）

**诉求**：「进度轮询再加个百分比显示呢」→ 因 8 个步骤**不等时长**（`downloading` 单次上限 180s、`running_sql` 无上限，这两段占绝大部分时间），纯按步骤序号算会长时间停在 25% / 75%，所以先问算法；用户选 **步骤百分比 + SQL 真实进度**。

**改动 3 个文件**
1. `UpgradeService::dashboard()`：`interrupted` 增 `'sql_total' => max(0, (int)($status['sql_total'] ?? 0))` 与 `'sql_completed' => is_array(...) ? count(...) : 0`。`sql_total` 在 `run()` 的 `verified` 阶段就已写入，所以进 `running_sql` 时一定有值。
2. `index.html`：`.upgrade-progress` 首位加 `<span class="upgrade-progress-percent"></span>` + 对应 CSS（`min-width:42px` + `text-align:right` + 等宽字体，避免位数变化时右侧步骤条抖动）。**放在第一个 step 之前不会破坏箭头**——`+` 相邻选择器只在前一个兄弟也是 step 时才加箭头。
3. `upgrade.js`：`renderProgress(state, sqlCompleted, sqlTotal)` 三参；`ratio = (state === "running_sql" && sqlTotal > 0) ? min(c/t, 1) : 1`；`percent = round((index + ratio) / steps.length * 100)`。轮询处传 `data.sql_completed, data.sql_total`；页面加载路径只传 state（首轮轮询 2s 后补上）。

**公式为何这样**：非 SQL 阶段 `ratio=1` → `(index+1)/8`；SQL 阶段 `ratio=completed/total` → `(index + ratio)/8`，在 `ratio=0` 时等于上一步的 `(index)/8`，**与前一阶段无缝衔接**。实测：13→25→38→50→63→75→88→100 单调；SQL 7 条时 63→63→64→66→68→70→71→73→75 连续；无 SQL 时 63→88 直接跳；`9/7` 被 clamp 到 75%；无 `sql_total` 退回 75%；`recovering` 返回 null → 隐藏进度条。

## 回滚能力盘点与建议（16:53，**仅建议，未改代码**）

**用户问**：「当前没提供回滚按钮吗」→ 追问「你觉得哪种更符合正常升级流程」。

**现状（查证结论）**
- 有 `.btn-recover`「恢复升级现场」（`index.html:166`），只在**中断告警**里出现，条件是 `recoverable`（= `upgradeLockHeld()` 为假）。
- `recover()`（`:210-218`）接受 `preparing`/`downloading`/`verified`/`backing_up`/`applying_files`/`running_sql`/`committing`/`recovering`/`needs_repair`/`done`，**但对 `done` 额外要求维护锁仍归属该批次**，否则抛「已完成的升级批次不需要恢复。」→ **正常跑完的升级没有回滚入口，是有意的。**
- 原因：`restoreBatch()`（`:1182-1199`）只要 `sql_started` 为真就 `restoreDatabase()` → **用升级前备份整库覆盖**。中断批次的窗口极小（维护锁已暂停写入）；已完成批次已带新代码跑了一段时间，整库回滚会**丢掉升级后写入的所有数据**。
- **顺带发现一处不一致**：`recover()` 只调 `restoreBatch()`，**不调 `writeVersion()`**；而 `buildFilePlan()` 的 journal 只覆盖升级包 `payload/` 里的文件 → **版本号不回退**。中断在 `running_sql` 等早期阶段没问题（`writeVersion()` 还没跑），但若中断恰落在 `writeVersion()` 与 `done` 之间，恢复后会出现「文件已回退、版本号仍是新版」。

**我的建议：只允许「未执行过 SQL」的已完成批次回滚。** 理由：
1. 无 SQL 的升级 = 纯文件替换，数据库未动 → `restoreBatch()` 里的 `restoreDatabase()` 分支压根不走 → **零数据丢失风险**，且现有的 `recover()` 已原生支持这种情况，只需放宽 `done` 的守卫条件（`sql_total === 0` 时放行）。
2. 覆盖真实场景：改模板/前端的低风险升级，升级后发现问题想退回旧版。
3. 有 SQL 的升级一旦成功，数据库已演进 —— 旧代码配新库结构会崩，此时「回滚」在语义上不成立。
4. **把「整库覆盖」做成常规升级流程里的一个按钮是反模式**：标着「回滚」的按钮会让用户以为是安全撤销，而它实际会丢数据。「回滚前先备份当前库」只让回滚可逆，**并不能阻止丢数据**。这类只能作为独立的**灾难恢复**功能单独设计（明确列出会丢多少数据、要求输入批次号二次确认等）。

**判断依据（供日后复用）**：升级流程里的「回滚」只应在**风险可控的边界内**提供；一旦升级成功且数据库已演进，退回旧版就是灾难恢复，不该混进常规升级流程。

### 主流系统的做法（用户追问「其它系统一般怎么处理」后补充）

| 系统 | 回滚方式 | 数据库 |
|---|---|---|
| WordPress 插件回滚 | **重新下载旧版安装包**覆盖安装 | 不碰 |
| Composer / npm | `install` 回 `lock` 文件 | 不涉及 |
| K8s / 蓝绿部署 | 切回上一个镜像 tag | **靠 expand-contract 迁移设计，库无需回退** |
| Rails / Django / Laravel | `migrate:rollback` | 每个迁移实现 `down()`，**成对回退** |
| Nextcloud / Magento | **不提供降级**，只能从备份整站恢复 | 整库还原（官方明确警告会丢数据） |
| 各类自动更新器 | 只在**升级未完成**时自动回滚 | 未对外服务，无数据损失 |

**三条共识**
1. **回滚的正统形态是「向前安装一个旧版本」，不是「用备份把状态倒带」** —— 备份倒带会丢数据，重装旧版明确且可重复。
2. **数据库靠「迁移可逆」或「向前兼容」解决，不靠整库还原**（K8s 圈用 expand-contract：先加列 → 部署新代码 → 稳定后再删旧列，这样代码回滚时库根本不用动）。
3. **升级前备份是灾难恢复的底牌，不是常规回滚手段**。

**对照本项目**：失败自动回滚（`failed_rolled_back`）+ 中断可「恢复升级现场」= 已是标准做法；**缺的正是「安装旧版本」这条正统路径** —— 因为 `run()` 硬性要求 `version_compare($latest['version'], $fromVersion, '>')`，目标版本必须**高于**当前版本，装不上旧版包。而「用备份整库倒带」主流系统恰恰不提供。

**修正后的建议**
- **短期（低风险）**：只允许**未执行过 SQL** 的已完成批次做文件回滚（零数据丢失，复用现有 `restoreBatch()`）。
- **长期（正统）**：把回滚做成「**安装旧版本包**」—— 放宽 `run()` 的版本递增校验，允许目标版本低于当前版本；旧版本包自带向下迁移 SQL，代码与数据库成对回退，完全不依赖备份倒带。前提是发布流程要为每个版本准备向下迁移 SQL，且**并非所有变更可逆**（删表/删数据类不可逆）。

## 皮肤 btn-group 切换组选中态（三皮肤统一）

**问题**：三个自建皮肤都把 `.btn-info` 与 `.btn-info.active` 写成**同色同 `!important`**（white `#165dff`／gray-light `#57534e`／sky-light `#0369a1`）→ 插件页「全部/免费/付费/本地」筛选组选中与未选中完全同色，选中反馈丢失。Bootstrap 基线本有层次（`#1688f1` → active `#0c6ec8`），是皮肤为统一色调抹平的，非回归。

**修法**（三皮肤各 +16 行，插在各自 `/* 5. btn-info */` 块之后、`/* 6. label-info */` 之前）：

```css
    background-color: #fff !important; border-color: <浅描边> !important; color: <主色> !important;

/* 成对补 :hover / :focus → 浅底 <hover底> + 主色描边 */
```

1. `:has(>.btn-info.active)` 是唯一能「只命中有选中项的按钮组」的判据。全站 4 类 `.btn-group`（插件筛选组、插件列表「安装+下拉箭头」、批量操作 dropdown、分页组）里**只有筛选组有 active**，不用 `:has()` 会误伤其余三类。浏览器不支持时整条静默失效，不误伤。

**这不是新引入的缺陷，是被暴露的既有问题**：`skin-white.css:60-62` 的 `.skin-white button{outline:none!important}` **只匹配 `<button>`，不匹配 FastAdmin 主流的 `<a class="btn">`** → `<a>` 一直保留 UA 焦点环。同一页 `<button>` 的 active+focus 是 `outline:none`，`<a>` 是 `auto 5px`。

**修法**：切换组补 `.btn-group:has(>.btn-info.active)>.btn-info{outline:none!important}`（(0,5,0)+`!important` 压过 `.btn:active:focus` 的 (0,3,0)），**覆盖组内全部按钮含选中态**，焦点反馈由描边/底色变化承担。范围经用户确认为「只改切换组」，全站其他 `<a class="btn">` 保持现状（实心蓝上黑环不明显）。

**复测结果**：三皮肤 × 5 种伪类（none/hover/focus/active/active+focus），`#t-all` 与 `#t-free` 全部 `outline=none`；对照组 `#g-1`（无 active 的按钮组）仍为 `auto 5px`（符合既定范围），`#b-plain`（`<button>`）始终 `none`。

### 未选中态中性化（用户选定方案 1）

用户反馈未选中是蓝字、问改黑是否更好。结论：**只改字色会变成「灰字配蓝边」的混搭**，应整体中性化。最终方案（Ant Design Segmented 的标准做法）：**未选中态三皮肤统一为中性** —— 字 `#1d2129`（正文色）+ 描边 `#dcdfe6`（中性描边）+ 白底；**主色只留给 hover 与选中**。hover 仍用各皮肤主色（white `#165dff`/`#f0f5ff`，gray-light `#57534e`/`#f4f3f1`，sky-light `#0369a1`/`#eff6fd`）。

被否掉的方案：只改字色保留蓝边（混搭、各皮肤观感不一致）；字 `#4e5969` 次级灰（易被误读为禁用）。

**关键收益**：未选中态不再随皮肤变化 → 三皮肤在这部分**完全一致**，皮肤差异只体现在 hover/选中。实测确认 `#t-free` 常态三皮肤均为 `rgb(29,33,41) / #fff / rgb(220,223,230)`。

**验证要点**：本次只替换两个色值字面量（选择器与特异性未动），但选择器权重撞车风险与色值无关，因此实测仍有必要 —— 复测确认 hover/选中/对照元素（`#g-1`、`#c-userinfo`）全部未受影响。
