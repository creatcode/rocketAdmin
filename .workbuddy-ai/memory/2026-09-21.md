## skin-white 主题全局样式审查

对 rocket-admin 后台默认主题 skin-white 做了全面模板样式审查（只读，未改动文件）。

### 主题加载链路（已确认）
- 默认皮肤：`config/rocket.php` 的 `adminskin => ''`，模板中 `|default='skin-white'` 兜底 → body class = `skin-white`。
- 样式入口：`app/admin/view/common/meta.html` 只加载 `public/assets/css/backend{.min}.css`；因 `adminskin` 为空，额外的 skin link 分支不输出。
- `backend.css`（源码）是 `@import` 清单，`skin-white.css` 在**第 3 行**导入，其后还有 fastadmin.css 之外的 12 个第三方库。
- `backend.min.css` 是打包产物（含已内联的 skin-white 规则，34 处 `#165dff`）；`.env` 当前 `APP_DEBUG=true` → 实际走 `backend.css` 源码路径。

### 核心问题（优先级排序）
1. **P0 构建产物不同步风险**：`backend.css` 是 @import 清单，`backend.min.css` 是内联包。两边不同步时，切 debug 开关会导致皮肤表现不一致。且 `skin-white.css.bak` 与正式文件已有 74 行差异。
2. **P0 基础层硬编码品牌色未参数化**：`fastadmin.css` 中 `#18bc9c`(22处)、`#f75444`(23处)、`#f39c12`(21处) 直接写死，无皮肤前缀。skin-white 只覆盖了其中极少部分。
3. **P1 组件覆盖缺口**（fastadmin/bootstrap 有定义、skin-white 完全未覆盖）：`badge`(23)、`alert`(34)、`progress-bar`(33)、`callout`(19)、`modal`(47)、`breadcrumb`(8)、`list-group`、`checkbox`。
4. **P1 bootstrap.css 的 label 定义冲突**：`.label-success{background:#18bc9c}`、`.label-primary{background:#444c69}`、`.label-warning{#f39c12}`、`.label-danger{#f75444}`（bootstrap.css 4859-4892 行）。skin-white 用 `.label-success{color:#18bc9c;background:rgba(...,0.1)}` 覆盖了文字色和底色，属"半覆盖"状态。
5. **P2 第三方库主题色未纳管**：layer.css 写死 `#009f95`/`#1e9fff`；nice-validator、bootstrap-select 等各自有独立配色。
6. **P2 图表色硬编码**：`public/assets/js/backend/dashboard.js:14-20` 直接把 echarts 色板写成 `#18d1b1/#3fb1e3/...`，与主题蓝 `#165dff` 无关。

### 结论
skin-white **不能**保证全局样式颜色一致。它只覆盖了 head/sidebar/tabs/table/pagination/panel/btn 等主干组件，基础层三套品牌色并存（`#165dff` 主题蓝 / `#18bc9c` 青 / `#444c69` 灰蓝），且 badge/alert/progress/callout/modal 等组件仍是 bootstrap+fastadmin 的原生配色。

### 架构约束（用户纠正后确认，重要）
皮肤隔离机制决定了修复边界，**不能动公共基线**：
- `bootstrap.css` / `fastadmin.css` 被全部 20 个皮肤共用，加 `.skin-white` 前缀会污染其它皮肤。
- less 目录中**没有 `skin-white.less`**，该皮肤是纯手写 CSS，脱离 less 构建链。
- 皮肤间唯一隔离手段 = 选择器前缀：`.skin-white`（外层框架）/ `body.inside-header`（iframe 内页面）。
- body class 有两套：外层 `class="... skin-white ..."`（`app/admin/view/index/index.html:7`），iframe 内 `class="inside-header inside-aside"`（`app/admin/view/layout/default.html:7`）。补规则必须两套前缀成对写。
- 结论：所有修复只能收敛在 `public/assets/css/skins/skin-white.css` 内，靠前缀 + 必要时 `!important` 压过基线。

## 回归缺陷修复：按钮字色丢失（同日发现并修复）

### 现象
用户反馈「按钮里面的字体没颜色了」。

### 根因（特异性倒置）
上一轮我新增的 `.skin-white a { color: #165dff }` **特异性 0,2,0**，
压过了基线所有按钮文字色声明（**特异性仅 0,1,0**，bootstrap.css:3012 起）。

而 FastAdmin 的工具栏/表格操作按钮**是用 `<a>` 实现的**：
- `public/assets/js/require-table.js:169` — `<a href="javascript:" class="btn btn-warning-light ...">`
- `public/assets/js/require-table.js:93-107` — `btn-editone`/`btn-delone`/`btn-dragsort`

→ 实心按钮（primary/success/danger）与浅底按钮（`*-light`）文字被整片刷成主色蓝，出现「蓝字压蓝底」。

### 修复（skin-white.css 第 1b 节，按语义分支统一接管）
1. 实心 `btn-{primary,success,danger,warning,info}` → `#fff !important`
2. `btn-default` / `btn-link` → `#4e5969`，hover `#165dff`
3. 浅底 `*-light` 五分支恢复语义字色（fastadmin.css:2393+）：
   primary-light `#85878a` / success-light `#468847` / danger+error-light `#b94a48` /
   warning-light `#c09853` / info-light `#3a87ad`
4. `btn-outline` → 白字白边（顶栏深蓝底）
5. `btn-app` → `#666`，hover `#444`
6. `.btn` 系补 `text-decoration: none`，防全局 `a:hover` 下划线渗入

文件 1394 → 1510 行，括号配平 231/231。

### 验证方法（关键经验）
**做 CSS 回归验证必须真正回退文件做 A/B，不能靠注入 `!important` 模拟**——
注入的 `!important` 优先级低于皮肤里更晚出现的同权重 `!important`，两轮读数会完全相同，得出「无差异」的假结论。
正确做法：把 legacy 版与 fixed 版依次写盘 + `Page.reload({ignoreCache:true})` + `Network.setCacheDisabled(true)`，逐轮实测。

实测结果（改动前 → 改动后）：
| 按钮 | 前 | 后 |
|---|---|---|
| `btn-success btn-add` | `rgb(22,93,255)` 蓝 | `#fff` |
| `btn-danger btn-del` | `rgb(22,93,255)` 蓝 | `#fff` |
| `btn-warning-light` | `rgb(22,93,255)` 蓝 | `rgb(192,152,83)` |
| `btn-success btn-editone` | `rgb(22,93,255)` 蓝 | `#fff` |

### 影响面排查（确认未误伤非按钮元素）
分页 `.pagination>li>a`、标签页 `.nav-tabs>li>a`、下拉菜单、面包屑、表格内普通链接
——实测均保持原色，未被按钮规则波及。全量 15 个按钮，异常数 0。

### 经验教训（写入长期约定）
**给皮肤加全局元素选择器（`a` / `input` / `button` 等）前，必须排查该元素是否被其它组件复用。**
FastAdmin 大量使用 `<a class="btn ...">`，任何 `.skin-white a` 级别的规则都会命中按钮。
安全做法：同步补齐 `.btn` 家族的语义字色接管，或改用不命中 `.btn` 的选择器。

### ★ 重要发现：角标颜色是按 strlen 取模，不是按数量
`app/admin/library/AdminAuth.php:445-462`：
```php
$color = $colorArr[(is_numeric($nums) ? $nums : strlen($nums)) % $colorNums];
$badgeList[$url] = '<small class="'.$class.' pull-right bg-'.$color.'">'.$nums.'</small>';
```
- 数字角标 → 按数值取模
- **文字标签（如 `hot`）→ strlen('hot')=3 → colorArr[3]='blue' → bg-blue**

所以 `bg-blue` 同时服务两类角标。基线 `bg-blue` 在 fastadmin.css:5397 = `#1688f1 !important`（第四种蓝）。

### 处理
`.skin-white .bg-blue` 与 `.bg-light-blue` → `#165dff`（用户确认「统一成主色」）。
其余 6 色保留（承载计数递减辨识功能）。

实测配色板：red `rgb(247,84,68)` / green `rgb(24,188,156)` / yellow `rgb(243,156,18)` /
**blue `rgb(22,93,255)`（已收敛）** / teal `rgb(57,204,204)` / orange `rgb(255,133,27)` / purple `rgb(96,92,168)`

### 状态

## 第四轮：回退「顶部标签页实心背景」过度改动

### 用户反馈
「顶部标签页为什么加上背景色了，之前没有啊」

### 真相（git 核对）
改动前**本来就有背景色** —— `background: #f0f5ff`（浅蓝），是项目原有设计。
我上一轮照着参考截图擅自改成了 **实心主色 `#165dff` + 白字**，那个深蓝底色就是"多出来的背景色"。
另顺手给 `:hover` 态也加了 `background: #f0f5ff`，同样是多余改动。

### 处理
还原为原始值：
```css
.skin-white .nav-addtabs>li.active>a {
    color: #165dff;
    background: #f0f5ff;      /* 还原为浅蓝，非实心主色 */
}
.skin-white .nav-addtabs>li:hover>a { color: #165dff; }   /* 去掉多余背景 */
```
实测确认：激活标签 `bg=rgb(240,245,255)` = `#f0f5ff` ✓
`git diff HEAD` 中标签页区块**已完全消失**，证明与原始版本一致。

### ★ 教训：参考截图 ≠ 授权改动
用户发参考截图说的是「参考下这个」，不等于「照这个改」。
我据自己审美把「浅蓝底蓝字」改成了「实心蓝底白字」，属于**超出授权的自主改动**，

### 根因：CSS 权重撞车（0,1,2 vs 0,1,2）
我在 §1 写的链接色规则 `body.inside-header a` 权重是 **0,1,2**
（1 类 `.inside-header` + 2 元素 `body` `a`）。
而 Bootstrap/FastAdmin 的**组件链接规则恰好全是 0,1,2**：
`.dropdown-menu > li > a`（bootstrap.css:3537）、`.pagination > li > a`（fastadmin.css）、
`.nav-tabs > li > a`、`.breadcrumb > li > a`。

同权重 → **后加载者胜**。`skin-white.css` 由 `backend.css` 最后 `@import`，
于是整族组件链接被静默染成主色：下拉菜单项、分页「上一页/下一页」全部变蓝。

### 修复
```css
.skin-white a:where(:not(.btn)),
.inside-header a:where(:not(.btn)) { color: #165dff; }
```
- `body.inside-header a` → `.inside-header a`：**0,1,2 → 0,1,1**，低于全部组件规则。
- 追加 `:where(:not(.btn))` 排除按钮。**必须用 `:where()` 而非 `:not()`** ——
  `:not(.btn)` 会把权重抬到 0,2,1，反而又盖过 0,1,2 的组件规则，制造新的撞车。
- §1b「按钮字色接管」（113 行）本就是为修补 §1 副作用而写，已整段删除。
  文件 1526 → 1426 行，`+248/-4`。

### 实测（headless Edge + CDP，cache-disabled，真实换文件 A/B）
本轮爆炸半径精确到 3 类元素，**零附带影响**：
| 元素 | 前 | 后 |
|---|---|---|
| 下拉菜单项（导出 JSON/XML/CSV…） | `#165dff` | `#333` |
| 下拉内 `.btn-link`（设为正常/设为隐藏） | `#4e5969` | `#333` |
| 分页 上一页/下一页 | `#165dff` | `#666` |

外框 `.skin-white` 作用域本轮前后 **0 差异**；5 个页面逐元素比对无其他变化。

### ★ 新增铁律（已写入 MEMORY.md）
给皮肤写全局元素选择器时，**权重必须严格低于组件规则**。
组件链接规则集中在 0,1,2 → 皮肤链接规则必须 ≤ 0,1,1。
排除类名用 `:where(:not(...))`，**不要用 `:not(...)`**（会抬升权重）。

### ★ 全高布局（本轮关键技术改动）
第一版用「自然文档流 + `min-height`」，结果是**页面底部留一大片灰、图表卡却撑不高**。
改成真正的全高链路：

```css
.dashboard-page { height: calc(100vh - 37px); overflow-y: auto;
                  display: flex; flex-direction: column; }
.dashboard-shell.panel      { flex: 1 0 auto; display: flex; flex-direction: column; }
.panel-body / .tab-content / .tab-pane.active { 同上，flex 链一路贯通 }
.dash-grid { flex: 1 0 auto;
             grid-template-rows: auto minmax(0, 1fr) auto; }   /* 中间行吸收多余高度 */
#echart { flex: 1 1 auto; min-height: 240px; }                 /* 图表随卡片长高 */
.dash-feed__item { flex: 1 0 auto; min-height: 48px; }          /* 列表行均匀铺满 */
```

要点：
- **`height` + `overflow-y: auto`** 才是对的组合。原版的 bug 是 `overflow: hidden`（裁切且不可达），
  不是定高本身。定高 + 可滚动 = 既铺满视口又永不裁切。
- 链条上统一用 **`flex: 1 0 auto`（不收缩）**，避免内容超高时被压扁；超高则由 `.dashboard-page` 滚动。
- `grid-template-rows` 中间行 `minmax(0, 1fr)`；窄屏降列时必须 `grid-template-rows: none` 复位。

### ★ 度量陷阱（本轮踩到）
判断「是否裁切」**不能拿绝对坐标比 `scrollHeight`**：

（有内部滚动时内容依然可达）。
